# Authentication

## Scope

The initial authentication foundation provides local email/password authentication for human users.

It deliberately does not implement public registration, MFA, OIDC, LDAP, or external identity providers yet. Password reset/recovery is implemented through short-lived single-use email links.

## Login flow

1. The application verifies that setup has completed.
2. HTTPS is required when configured.
3. A secure PHP session is started.
4. The submitted CSRF token is validated.
5. Login throttling is checked.
6. The user record is loaded by normalized email address.
7. Only active, non-deleted users may authenticate.
8. The password is verified with `password_verify()`.
9. Password hashes are upgraded automatically with `password_needs_rehash()`.
10. The session identifier is regenerated after successful authentication.
11. The authenticated user identity is stored in server-side session state.
12. The CSRF token is rotated.

The login endpoint returns one generic error for invalid credentials. It does not reveal whether an account exists.

## Password storage

Passwords are never stored in plaintext.

Open Phonebook uses PHP's `PASSWORD_DEFAULT` algorithm so the password storage format can evolve with supported PHP versions.

The installer currently requires at least 12 password characters for the initial administrator.

## Password reset and account recovery

The login page links to a password-reset request form.

Request behavior is deliberately enumeration-resistant:

- the same public confirmation is shown whether an active account exists or not
- invalid, unknown, inactive, or deleted accounts do not create reset records
- one account can receive at most one new reset request within five minutes
- POST responses are padded to a minimum duration to reduce simple account-existence timing differences
- mail-delivery failures are not exposed to the requester

Reset tokens are:

- 256-bit random values
- valid for 30 minutes
- single-use
- stored only as a domain-separated HMAC-SHA-256 hash
- never placed in query strings

Reset links use a URL fragment:

`/password-reset/#<token>`

The fragment is not sent in the HTTP request. Same-origin JavaScript removes it from browser history and submits it through a CSRF-protected POST. The plaintext token then remains only in the server-side reset session until completion or expiry.

A successful reset changes the password and increments the user's `auth_revision` atomically. Every authenticated browser session carries the revision from login and revalidates it against the database. A revision mismatch invalidates the session, so changing a password through recovery signs out all previously authenticated browser sessions.

The reset password must contain at least 12 characters and is stored with `password_hash()`.

System-generated reset mail uses the configured `mail.from` / `OPENPHONEBOOK_MAIL_FROM` sender and requires an HTTPS `app.base_url`.

## Session model

Browser sessions use:

- cookies only
- HttpOnly cookies
- SameSite=Lax
- Secure cookies on HTTPS
- PHP strict session mode
- session identifier regeneration after login and logout
- current account-state and authentication-revision validation on protected browser requests

The session stores only the minimum authenticated identity needed by the current application layer:

- user ID
- email
- display name
- role
- locale
- timezone
- authentication timestamp

These cookie protections are security invariants in code, not operator-tunable configuration. Open Phonebook deliberately does not expose settings that could disable HttpOnly or weaken SameSite behavior. The Secure flag follows the actual HTTPS request used to start the session, while production runtime normally requires HTTPS.

Authorization must still be checked server-side for every protected operation. Session presence alone does not grant access to arbitrary resources.

## Login throttling

Failed login attempts are throttled using a database-backed bucket keyed by an HMAC of:

- normalized email
- client IP address

The raw email/IP combination is not persisted in the throttling table.

Initial policy:

- five failed attempts
- 15-minute observation window
- 15-minute block

A successful login clears the bucket for that email/IP combination.

The application key used for HMAC generation is generated during setup and stored outside the database in runtime configuration. It may alternatively be supplied through `OPENPHONEBOOK_APP_KEY`.

## Application key

The application key is a random secret generated by the setup installer.

It is not a user password and must not be committed to Git.

Current uses include privacy-preserving keyed hashes for security controls. Future cryptographic uses must document their own key-separation requirements rather than blindly reusing the same derived value.

## Logout

Logout is POST-only and requires a valid CSRF token.

The authenticated identity is removed, the session identifier is regenerated, and the CSRF token is rotated.

## Localization

Authentication UI strings are loaded through translation keys.

Initial locales:

- English
- German

Development-facing identifiers remain English.
